Tell me about a technically complex problem you solved.
Dive DeepInvent & SimplifyDeliver ResultsOwnership
★ Situation
I was working on a feature that let users control up to 12 soundbars at the same time from one screen. The app would ask every device "what's your state?" every 2 seconds — all 12 of them. Imagine sending 360 messages a minute to devices just to check if anything changed. The screen felt sluggish, sometimes froze, and there were crashes because updates from multiple devices were colliding with each other.
★ Task
My job was to make it feel real-time — less than 200ms response — without changing anything on the device firmware side, since those devices are already out in customers' homes.
★ Action
  • First I measured where the time was actually going, rather than guessing. I used Android's profiling tool and found two things: the main thread was spending most of its time decoding device responses, and the app was creating and throwing away large amounts of temporary data on every poll cycle.
  • Then I flipped the model entirely. Instead of the app constantly asking devices for updates, I made devices speak up only when something actually changed — like switching from a group chat where everyone's talking at once, to a system where people only raise their hand when they have something new to say.
  • Stop polling, and move all device response processing off the main thread. Once the app switched to just listening on the socket, it only did work when a device actually had something to say.
  • For the equalizer screen specifically, I made sure that adjusting the bass slider only redraws the bass slider — not the entire equalizer panel.
★ Result
  • Response time dropped from ~800ms to under 100ms — an 87% improvement, well past the 200ms target.
  • Device messages dropped by 92% — from 360 per minute to about 30.
  • App crashes went from 3–4 per month to zero for the next 6 months.
  • Two other Samsung teams adopted the same approach for their own device-control apps.
Follow-up Questions
Q1: How did you actually find where the slowness was coming from?
Used Android Studio's built-in profiler — like a real-time activity monitor. Recorded what the main thread was doing during a 30-second test. The visual breakdown showed it was spending most time decoding JSON responses from devices — that was the smoking gun.
If they dig deeperCPU tab, Sample Java/Kotlin mode, flame chart. Gson deserialization was the widest bar at 35-40% of main thread time. Memory tab showed regular spike of temporary object creation every 2 seconds — one spike per poll cycle, all thrown away immediately. Both signals pointed to the same fix: remove the polling.
Q2: How did you make sure devices only send updates when something changes?
Each device already sends an update over its open socket whenever something changes. I restructured the app to listen for those updates rather than ask for them. Used Kotlin's coroutine system to run 12 listeners simultaneously in the background without blocking the screen.
If they dig deeperEach device got a Repository with a StateFlow. MSF socket listener ran on IO dispatcher, deserialized off main thread, emitted into StateFlow. All 12 flows merged via combine() into one aggregated flow the ViewModel subscribes to.
Q3: What about when a device goes offline mid-session?
Built a simple state machine per device: connected, reconnecting, failed. Retry with exponential backoff — 1s, 2s, 4s — rather than hammering the device. One device going offline didn't affect the other 11 at all.
If they dig deepersupervisorScope per device so child coroutine failure doesn't propagate. Exponential backoff: 1s, 2s, 4s, 8s, max 5 attempts. On failure, UI shows 'Device offline' for that card only. On app foreground, mDNS re-discovery triggered.
Q4: What would this look like at 10x scale — say 1000 devices?
At that scale you'd need a different mental model — a central hub that tracks all device states, and the app subscribes to the hub. On the screen side, only load state for devices actually visible; everything else shows last known value from local storage.
If they dig deeperHub-and-spoke: SmartThings-style hub manages device state server-side, app subscribes via WebSocket. Client: virtual scrolling with Paging 3, device-scoped ViewModel pool, off-screen devices served from Room cache.
Q5: Why not just use LiveData instead of what you used?
LiveData is great for simple one-source, one-screen scenarios. But combining 12 separate streams, filtering them, transforming them — LiveData doesn't compose well for that. StateFlow is built for exactly this kind of reactive pipeline and works cleanly across all app layers.
If they dig deeperStateFlow: coroutine-native, supports operators (combine, filter, debounce), works in Repository/UseCase layers, testable with Turbine. LiveData requires MediatorLiveData for multi-source — unmanageable at 12 sources.
🧠 Memory Trick THE F5 PROBLEM. Old code = hitting F5 on a webpage every 2 seconds. Your fix = the webpage tells you when it updates. Everything else follows from that one insight.

Describe a time you made a difficult technical trade-off.
Are Right, A LotDive DeepCustomer ObsessionOwnership
★ Situation
At Samsung R&D, I worked on an internal Android tool that let engineers retrieve diagnostic information from Samsung Smart TVs over the local network. To fetch this data, the app had to first authenticate with an internal Samsung server which issued a short-lived access token — like a visitor badge at an office.
★ Task
Decide how to cache the authentication token: fetch fresh every launch (always valid, but adds 300–500ms delay) or store it for 24 hours (instant repeat launches, but introduces security and expiry risks). I had to make the right call, document it, and build it.
★ Action
  • I chose Option B — store and reuse — but addressed both risks deliberately. For security: I used Android's hardware-backed secure vault to store the token encrypted. Even if someone extracted the app's files, they couldn't read it.
  • For the expiry problem: rather than waiting for an engineer to hit an auth error mid-session, I check the token's remaining validity silently on app start. If within one hour of expiry, I refresh it quietly in the background before the engineer ever touches the screen.
  • I wrote a short design note covering both options, the risks, and my reasoning — so my tech lead had full visibility and future engineers would understand the trade-off.
★ Result
  • Every repeat launch within the 24-hour window made zero network calls for authentication — 100% of those calls eliminated. The tool opened and was ready to use instantly.
  • No engineer ever saw an authentication error mid-session because of the background refresh.
  • The caching pattern was later reused for a second internal Samsung tool with the same authentication requirement, with zero rework.
  • My tech lead appreciated the written reasoning — when a similar question came up for another tool, we had a documented decision to refer back to.
Follow-up Questions
Q1: Why 24 hours specifically? How did you arrive at that number?
The Samsung internal auth server told me directly — its response included an expires_in field set to 86,400 seconds, exactly 24 hours. I matched my cache TTL to that. Going shorter means unnecessary refresh calls. Going longer means using a token the server already considers expired.
If they dig deeperCache key stored alongside token in DataStore: token_fetched_at (epoch ms). On app start: if (current_time - token_fetched_at) > (86400 - 3600) seconds, trigger background refresh. The 1-hour buffer ensures the token is always valid during a full diagnostic session.
Q2: This is an internal tool — does security really matter that much here?
More than you'd expect. The token authorises access to internal Samsung TV diagnostics — firmware details, hardware identifiers, error logs on pre-release TV models in some cases. Hardware-backed storage means the encryption key never leaves the device chip — it cannot be extracted even from a full device backup.
If they dig deeperAndroid Keystore: keys stored in hardware-backed TEE. Token encrypted with AES-GCM 256-bit via Jetpack Security MasterKey. Stored in DataStore rather than SharedPreferences because DataStore write is a suspending function that throws on failure — SharedPreferences apply() is fire-and-forget, meaning silent failure on corrupt or missing token.
Q3: What if the auth server invalidates the token early — say, after a password reset?
Handled at the API call level: if a TV data request returns a 401, the app clears the cached token, fetches a fresh one, and retries the original request automatically. The engineer sees a brief pause, not an error screen. One extra round trip in this rare case, in exchange for zero round trips every normal launch.
🧠 Memory Trick VISITOR BADGE. Fresh badge every visit = always valid, but queues at reception slow everyone down. Stored badge = walk straight in. You stored it in a vault and checked it silently before anyone needed it.

Tell me about a time you improved performance of an existing system.
Dive DeepDeliver ResultsInvent & SimplifyCustomer Obsession
★ Situation
During my internship, I was asked to fix the file upload feature in an internal tool. It was slow — uploading a single image took 8 to 12 seconds on average — and about 1 in 7 uploads failed on a shaky Wi-Fi connection. The app would also sometimes freeze completely during an upload.
★ Task
Make uploads faster and more reliable within 6 weeks, working independently.
★ Action
  • I started by measuring, not guessing. The profiler showed that 70% of the upload time wasn't even the network — it was preparing the file. Images were being sent at their full original size, uncompressed, straight off the camera.
  • I added compression. After testing different quality levels with 10 colleagues in a blind comparison, quality 85 turned out to be the sweet spot — no one could tell the difference from the original, but the file size dropped by about 60%.
  • The freezing issue was because all of this was happening on the main app thread. I moved it all to a background thread, which fixed the freezes immediately.
  • For reliability, I split each upload into 1MB chunks. If the connection dropped halfway through, only the failed chunk had to retry — not the whole thing.
★ Result
  • Upload time: 8–12 seconds down to 3–4 seconds — about 62% faster.
  • Failure rate: from 15% down to under 3%.
  • Zero freezes reported after the fix.
  • The compression approach was reused in two other parts of the codebase.
Follow-up Questions
Q1: How did you actually use the profiler to find the bottleneck?
Android Studio's profiler shows a timeline of what every thread is doing. Triggered one upload and watched the recording. The main thread — which should be idle during an upload — was completely blocked for several seconds. Drilling in showed image processing work. Network tab confirmed huge payload sizes: 3-8MB per image.
If they dig deeperCPU tab, Sample Java/Kotlin. Flame chart: FileInputStream.read() and BitmapFactory.decodeStream() dominating main thread. Memory tab: raw Bitmap allocations of 3-8MB per image. Network tab confirmed 3-8MB uncompressed vs 1-3MB after compression.
Q2: How did you pick quality 85 — that seems like a specific number?
Ran a simple test. Compressed 10 images at different quality levels — 70, 80, 85, 90 — and showed pairs to 10 colleagues without telling them which was which. At 85, nobody could spot the compressed version. At 80, three people could. So 85 was the lowest level with genuinely indistinguishable quality.
If they dig deeperSSIM (Structural Similarity Index) could automate this — start at 95, decrement by 5 until SSIM drops below 0.97. 0.97 is the standard 'perceptually lossless' threshold. Implementable in Android without a library via pixel comparison.
Q3: What about large video files — does your approach work there?
Video needs a different strategy. Transcode the video first using the phone's hardware encoder — Android has a built-in API for that. For large files, upload multiple chunks in parallel — 3-4 at the same time — which can cut upload time significantly on a good connection.
If they dig deeperMediaCodec API for hardware-accelerated H.264 transcoding at CRF 23. Parallel multipart upload: backend issues N presigned URLs for N chunks, client uploads 3-4 chunks concurrently using async in coroutineScope, backend assembles by ETag.
🧠 Memory Trick MEASURE FIRST — the slowness wasn't the network, it was the prep work. Big unshrunk images sent raw. Compress, background, chunk. In that order.

Tell me about a time you disagreed with a technical decision.
Have Backbone, Disagree & CommitAre Right, A LotDive DeepEarn Trust
★ Situation
We were building the equalizer screen in the Samsung Sound App, where users adjust bass, treble, and mid levels on their soundbar. The initial plan was to send a device command on every slider movement so users could hear changes instantly.
★ Task
I disagreed and I needed to explain why this approach would create performance issues and propose a solution that preserved responsiveness without overwhelming the device..
★ Action
  • Instead of debating it theoretically, I recorded a demo on a test device. During a fast drag, the UI slider visually landed at 80%, but because dozens of commands were being sent in rapid succession, the soundbar processed them with delay and actually settled around 45%.
  • I proposed adding a 300ms debounce: the slider would continue moving smoothly on screen for immediate visual feedback, but the command would only be sent to the device once there had been no movement for 300ms, or when the user released the slider.
  • This ensured that quick drags generated only one final command, while slower deliberate adjustments still felt responsive.
  • I walked my tech lead through the demo and explained that this preserved the real-time user experience while preventing command flooding.
★ Result
  • The demo made the issue clear, and we adopted the 300ms debounce approach.
  • The equalizer shipped with zero reports of settings landing incorrectly, and device response latency stayed under 100ms. My tech lead later mentioned that seeing the behavior on the device was what changed his mind.
  • That experience reinforced an important lesson for me: when discussing technical tradeoffs, a concrete demonstration is often far more effective than just explaining the problem.
Follow-up Questions
Q1: Why 300ms specifically? How did you arrive at that number?
Tested a few values with the actual device — 100ms, 200ms, 300ms, 500ms. At 100-200ms, a moderately fast drag still fired multiple commands and the device still struggled. At 500ms, slow deliberate adjustments felt laggy. 300ms was where fast drags fired exactly one command on release, and slow adjustments still felt immediate. An empirical choice, not theoretical.
Q2: What if the user wants to hear the change while dragging slowly — does 300ms feel too slow?
In practice, no. The slider on screen moves instantly because we update the UI immediately on every touch event — only the command to the device is held back. So the visual feels live even if the audio lags very slightly. Tested internally and nobody noticed the delay.
If they dig deeperStandard technique called debouncing. The UI state and the device command are deliberately decoupled — UI updates on every frame, command fires only after the value settles. In Jetpack Compose this is implemented with a debounce operator on the slider value flow before it hits the command-sending layer.
Q3: What if your tech lead had not agreed even after the demo?
Would have implemented the fire-on-every-event approach as decided, but added a rate limiter in the MSF command layer as a safety guard — something that drops commands if more than a certain number arrive within a fixed window. That way the device is protected regardless of what the UI does. Disagree and commit does not mean abandon your concern — it means find a way to protect against the risk within the agreed approach.
🧠 Memory Trick THE DEMO BEATS THE ARGUMENT. Slider at 80% on screen, device playing at 45%. You recorded it, showed it, and that was the whole case. 300ms wait = fast drags don't flood the device, slow drags still feel live.

★ Situation
I was asked to build a 'Spotify integration' for the Samsung Sound App. That was the entire brief. No design, no spec, no definition of what 'integration' meant. Did it mean just opening Spotify? Linking to the current song? Full two-way control?
★ Task
Figure out what to build, align with stakeholders quickly, and deliver in one week.
★ Action
  • Before any meetings, I spent half a day figuring out what was actually possible. Spotify has a way to deep-link directly to a track from Android, and the app already had access to what song was currently playing on the soundbar through device metadata. That opened up three realistic options.
  • I wrote a one-page doc: Option A — just open Spotify (half a day), Option B — open Spotify on the exact song playing (3 days), Option C — full two-way control (2 weeks, needs cloud infrastructure we didn't have).
  • 15-minute meeting. Team picked Option B. I built it: read the current track from the soundbar's metadata, construct the deep link, open Spotify at that exact song. Fallback to Spotify's home screen if track info wasn't available.
★ Result
  • Delivered in 4 days.
  • The options doc format became a template the team reused for three other unclear feature requests that quarter.
Follow-up Questions
Q1: How does the app know what song is playing on the soundbar?
The MSF protocol includes now-playing metadata — track name, artist, and source URI. When a song is playing via Spotify on the soundbar, that URI is in Spotify's format, so you can extract the track ID from it and construct the deep link. If the soundbar is playing local music, the URI doesn't match Spotify's format, and the feature falls back to just opening Spotify's home screen.
If they dig deeperMSF DLNA/UPnP metadata: dc:title, upnp:artist, res fields. For Spotify Connect playback, res URI format: spotify:track:4iV5W9uYEdYUVa79Axb7Rh. Regex parse to extract track ID. Non-Spotify URIs or null → fallback to launch Spotify main. Button label updates reactively via StateFlow: 'Open in Spotify' vs 'Open Spotify'.
Q2: What if Spotify changes how their deep links work?
Two safety nets. First, a remote switch that can disable the feature instantly without pushing an app update — takes about 30 seconds to flip and reaches all users. Second, an automated test that verifies the Spotify deep link works end to end, which runs in CI. If Spotify ever changes their format, that test breaks and the team gets notified before it ships.
If they dig deeperFirebase Remote Config boolean: spotify_deeplink_enabled. Propagation <60s. CI integration test: fires Intent with Spotify URI, asserts PackageManager resolves it to Spotify app activity. Failure = test fails = pipeline blocked.

Tell me about a time you had to learn something quickly.
Learn and Be CuriousDive DeepBias for ActionDeliver Results
★ Situation
At Samsung R&D, the product team asked me to add session tracking to an internal tool — specifically, they wanted to know how far users got through certain flows before closing the app. My first instinct was to fire a network call when the app detects it's being closed. It worked on my desk — but not in the real world.
★ Task
Deliver reliable session analytics that works even when Android kills the app due to memory pressure, which is how apps most commonly close in real usage.
★ Action
  • I spent a day reading about how Android actually handles app termination. The key insight: when Android kills an app, the process stops immediately — there's no opportunity for the app to run any more code. Any work in progress, including network calls, is simply abandoned.
  • The right solution was to hand the work to the operating system rather than the app. I used WorkManager, which is designed exactly for this: you register a task with it, and Android guarantees it will run even if the app is no longer alive.
  • Whenever a session milestone was reached, I saved that progress to local storage immediately. When the user finished or the app was closed, I scheduled a WorkManager task to send the saved session data to the server.
  • I made the conscious trade-off that WorkManager doesn't guarantee instant execution — a few minutes' delay on analytics was completely acceptable for this use case.
★ Result
  • Session data delivery went from unreliable — silently dropping events whenever Android killed the app — to consistently above 98% delivery rate, verified by comparing events sent on the client against events received on the server.
  • The broader lesson was more valuable than the feature: reliable background work in Android is an OS-level problem, not an app-level one. You solve it by handing the work to the right system.
Follow-up Questions
Q1: How did you discover the data was being lost? How did you confirm it?
Noticed the server was receiving far fewer events than the number of test sessions being run. At first assumed it was a server issue. But client-side logs showed events being created correctly — they just never arrived. Deliberately simulated Android killing the app using Android Studio's process termination button. The network call was in-flight, the process died, and nothing arrived on the server.
Q2: WorkManager does not run immediately — what if the analytics data was time-sensitive?
A conscious trade-off thought through before choosing WorkManager. This was internal analytics — the team used it to review weekly trends, not react in real time. A few minutes' delay was acceptable. If real-time was needed, I would have used a foreground service with a persistent notification — but that adds complexity and battery cost that this use case didn't justify.
Q3: What if the network is unavailable when WorkManager tries to send the data?
WorkManager handles this natively. Set a constraint that the task should only run when a network connection is available. If there's no network, WorkManager waits until connectivity returns and then runs it. The data stays in local storage in the meantime.
If they dig deeperConstraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED). WorkManager persists the task to a local database so it survives device reboots too. If the task fails, it retries with exponential backoff by default.
Q4: How do you approach learning something completely new under time pressure?
Three-step pattern: (1) Understand WHY your current approach doesn't work — not just that it doesn't work. (2) Read just enough documentation to build something that works end to end — a prototype, not production code. (3) Intentionally break the prototype to find edge cases before they find you in production. Always prototype before touching production code when learning something new.
🧠 Memory Trick THE SILENT FAILURE. First approach worked on your desk. Broke silently in the real world because Android killed the app mid-send. You cannot do reliable work after app close inside the app. You hand it to the OS. Save locally first, schedule delivery second.

Tell me about a failure and what you learned.
Learn and Be CuriousEarn TrustOwnershipDeliver Results
★ Situation
I was doing a freelance project — a prototype e-commerce Android app for a small business client. One feature was a flash sale: products showing a discounted price for a limited time with a countdown timer. The client had a hard deadline to show it to stakeholders.
★ Task
I scoped it, told them three days, and they planned around that date.
★ Action
  • The timer itself took a day as expected. But I had not thought through what happens when the timer hits zero. The cart and checkout had no mechanism to know the sale had ended — a user could add an item during the sale, the sale ends, and they'd check out at the discounted price.
  • Getting this right — making all active screens re-fetch their data the moment the timer expires, and handling the edge case of a user mid-checkout when it happens — took six more days. Nine days total instead of three.
  • I told the client as soon as I realized, not on the deadline day. I explained what I had underestimated and gave a revised date I was confident in.
  • I fixed the problem properly: when the sale timer expires, the app now broadcasts a refresh signal. Every open screen listens for it and re-fetches from the server immediately.

Tell me about a time you used data to drive a decision.

★ Situation
For my watch face app, I had to decide where to spend my next sprint: add 20 new watch faces, build a Favorites feature, or improve load time. I had no product manager, no user researcher — just Firebase Analytics data and Play Store reviews.
★ Task
Make a data-backed prioritization decision, and define what success would look like before building — not after.
★ Action
  • I looked at how users actually moved through the app. Users who browsed more than 10 watch faces spent four times as long in the app as users who browsed fewer. That drop-off suggested they were running out of content, not features.
  • I searched the Play Store reviews for patterns. 34 out of the last 100 mentioned wanting more watch faces. Only 6 mentioned Favorites, and 3 mentioned loading speed.
  • Before writing a single line of code, I set a specific target: if adding 20 watch faces is the right call, then within 30 days, the percentage of users browsing more than 10 watch faces should increase by at least 20%.
★ Result
  • The metric went up by 27% — above target.
  • Daily active users grew 18% in the same period.
  • Setting the success metric upfront meant I could honestly say whether the decision was right, not just look for confirming signals after the fact.
Follow-up Questions
Q1: How did you set up the analytics to get that insight?
Logged a custom event every time a user tapped on a watch face to preview it, with the watch face category as a parameter. Also tracked download completions. From these, built a funnel: browsed → downloaded. The interesting insight came from segmenting by how many items a user browsed — users who went beyond 10 behaved very differently from those who stopped early.
If they dig deeperFirebase Analytics: watch_face_viewed event (params: watch_face_id, category), watch_face_download_completed. Custom UserProperty: heavy_browser = views > 10 in session. Segmented session_duration by heavy vs light browsers in BigQuery. Result: 4.2 min vs 1.1 min average session.
Q2: What if the data had been inconclusive?
Fall back to first principles: what do people come to a watch face app for? Watch faces. When data is ambiguous, more of the core value is usually the safer bet. Also think about reversibility — adding content is easy to undo, a Favorites feature requires UI investment and migration logic. When uncertain, pick the more reversible option and re-evaluate.
If they dig deeperBezos two-door framework: Type 2 decisions (reversible) should be made fast with imperfect information. Content addition = Type 2. Favorites feature with local storage = harder to roll back. Default to reversible, high-confidence option. Set a shorter measurement window (2 weeks instead of 30 days) when less confident.
